## 3. Argument map：論証の分解

| 要素 | 本レポートの内容 |
| --- | --- |
| topic | AIとの対話で制作したウェブ実験デモにおける技術理解の反映 |
| question | 技術理解は今回の設計にどれほど、どのように現れたか |
| main claim | 実行場所・完了条件・複雑さの取捨選択への反映は強い。独立した専門技能全般と学習効果は判定できない |
| subclaims | 実行場所の区別が構成へ反映／保存完了と確認を分離／分岐を減らして分析材料を維持／教材目的が実験条件に影響 |
| evidence | Q004、Q038→Q041、Q059〜Q062、U012→Q033と対応する現行資料・コード |
| reasoning | 具体的な指示・変更前後・成果物の対応を確認する質的な事例分析。コードの存在だけから個人の能力を推定しない |
| conclusion / contribution | 機能数や専門用語数よりも、何を区別し、何を削り、何を残したかを評価対象にする |
| scope | 保存された10セッションと指定HEAD。サービス仕様の再調査、実行試験の再実施、受講者の学習評価は対象外 |
| stake | 講演でユーザーの判断とAIの寄与を誤って説明せず、次に何を実証すべきか明確にできる |

観察事実は「回答にこの文字列がある」「コードにこの処理がある」です。解釈は「これが理解の反映を支持する」です。検証すべき仮説は「その結果、説明しやすさや理解が改善した」です。この三層を混ぜないことが、論証の主要な点検基準です。

## 4. Paths to deepen the discussion

1. **簡略化とデータの意味の保持。** 残した複雑さが必要だったという主張を検討するには、再開・0回答・異なる刺激の分析例が必要です。ファイルやメタデータの存在だけでは有用性は示せません。
2. **教材目的と研究目的の緊張。** 参加者間条件への変更は教材目的の影響として支持できますが、受講者の理解の変化と研究上の利害は別に比較する必要があります。
3. **AIの提案とユーザーの介入。** ユーザーが変更した条件と、AI案をそのまま採用した条件を分け、説明・実装の理解を追加で確かめれば、寄与の帰属を精密にできます。
